# Comms spine: one projected ledger, per-channel lanes, inbound first

## Thesis
Channel becomes a field, not a collection. One append-only comms_events ledger carries a derived `lane` field, so decision A (Inbox tabs by channel) and decision B (unified household timeline) are the same query with a different WHERE clause, covered by four indexes, and a future channel ships by writing a new `channel` string into an existing `lane` with no migration and no client change. This is affordable exactly once, right now, because every comms collection in production is empty. Two commitments make the ledger safe rather than clever. First, every source collection stays in place as a write-only archive with zero readers, so the ledger is a projection for all six channels rather than a read model for two and a system of record for four, and rebuildCommsTimeline is total. Second, deletion ships in the same commit as the first write, because a projection with no delete path is how a data asset quietly becomes a liability, and this codebase currently has zero retention, purge or erasure constructs (verified by grep across MyTribe/functions/src). Fail-loud stops being a UI convention and becomes a schema guarantee: every broadcast miss is a durable row with status 'skipped' and a named statusReason, queryable and clickable, landing on the household's own timeline, so "5 skipped" can never again be a counter nobody can expand. And nothing is designed against an empty collection: slice 1 repoints both numbers off demo.twilio.com, which needs no carrier approval, so inbound texts, calls and voicemails start landing the day it ships. This beats "build the composer first, wire Twilio later," which has already been attempted and produced 651 lines of android Inbox and five parallel wasm streams rendering zero rows. It beats "five parallel queries merged per platform," which triples the timeline work and guarantees the three surfaces disagree.

## Data model
- NEW comms_events/{eventId}, the spine. Fields: channel ('sms'|'whatsapp'|'call'|'voicemail'|'email'|'portal'), lane ('messages'|'calls'|'email'), direction ('inbound'|'outbound'), kinfolkId (string, empty = unmatched inbound), kinfolkName (denormalized, empty when unmatched), occurredAtMs (epoch ms NUMBER, matching the existing convention at lib/conversations.ts:73-80, never a Timestamp), preview (140 chars, produced by previewOf at lib/conversations.ts:30 then run through the new scrubPreview helper), subject, status ('received'|'sent'|'delivered'|'read'|'skipped'|'failed'|'missed'|'no_answer'), statusReason (empty unless skipped or failed; one of 'suppressed'|'carrier_stop'|'optout_state_unknown'|'no_phone'|'no_email'|'no_sms_consent'|'not_onboarded'|'provider_error:<code>'), authorship ('operator'|'client'|'system'), provider, providerId, threadKey, broadcastId, inInbox (bool), unreadForAdmin (bool), needsReply (bool), media (array of {kind, durationSec, recordingSid}), sourceRef {collection, docId}, expiresAtMs (number|null), schemaVersion. Server-written only.
- comms_events design rules that carry the whole thesis. (1) `lane` is computed at write time, never derived at query time: sms/whatsapp/portal to 'messages', call/voicemail to 'calls', email to 'email'. That is what makes decision A one equality per tab. (2) eventId is DERIVED from the source id so every writer is idempotent and every replay upserts: sms:{SM...}, call:{CA...}, vm:{RE...}, portal:{kinfolkId}:{messageId}, ext:{externalMessageId}, bc:{broadcastId}:{kinfolkId}:{channel}. (3) `inInbox` is false for per-recipient broadcast rows, so a 34-household send puts ONE line in the Inbox and 34 lines across 34 household timelines. (4) `authorship` is set at write time and is the field you cannot retrofit: it is the only thing that will ever answer which message text is the operator's to reuse when someone wants to few-shot the Auntie voice generator on real history. It is free today and archaeology at 50,000 rows.
- READ PATTERN 1, Inbox tab (decision A): where lane == <tab> and inInbox == true order by occurredAtMs desc limit 200. READ PATTERN 2, household timeline (decision B): where kinfolkId == X order by occurredAtMs desc limit 50, cross-channel by construction. READ PATTERN 3, unread badge: where unreadForAdmin == true order by occurredAtMs desc. READ PATTERN 4, broadcast reach after the fact: where broadcastId == X order by occurredAtMs desc, which turns the perChannel counters at broadcastMessage.ts:294-308 into named durable rows. READ PATTERN 5, unmatched callers: where kinfolkId == '' order by occurredAtMs desc, reusing the kinfolkId index.
- SOURCE COLLECTIONS ARE KEPT, NOT RETIRED. sms_messages, calls_log and voicemails keep their existing twilioInbound.ts:210/:254/:298 writers unchanged and become write-only archives with every reader deleted. This is a deliberate reversal of two of the three candidate designs, and it is the single change that makes the projection claim honest: if the sources are retired, comms_events becomes the sole system of record for four of six channels while advertising the durability of a rebuildable read model. Keeping them costs nothing (0 docs today, one extra write per inbound event) and makes rebuildCommsTimeline total rather than partial. Their firestore.rules entries (:578, :626, :636) flip from 'read, write: if isAuntie()' to 'read: if false; write: if false' once inbound is verified live, so no client reads them and no client writes them.
- CHANGED conversations/{kinfolkId} and its messages subcollection. Schema unchanged, still the source of truth for the portal thread, keeps its 2 live docs. appendMessage (lib/conversations.ts:57-104) gains one more write INSIDE its existing transaction: the projected comms_events row, channel 'portal', lane 'messages'. Same-transaction means this projection can never drift. listConversations, getConversationThread and replyToConversation are untouched, so React Inbox.tsx and ConversationThread.tsx keep working through the entire redesign.
- CHANGED external_messages. Adds kinfolkId (id only, resolved to a display name at read time inside the callables). Deliberately NOT adding kinfolkName: the collection's whole premise is that recipientRedacted is unmappable, and writing the plaintext name in would cancel that control, go stale on rename, and survive a household erasure. Also adds bodyPreview (140 chars, scrubbed, mirroring conversations.lastMessagePreview) because the timeline and the broadcast detail view otherwise render 'Email sent, 412 characters', and adds errorCode plus errorMessage on failure, where today a failed send writes nothing at all. Full outbound bodies are never persisted. Engagement counters keep being incremented by providerMessageId at engagementWebhooks.ts:89-90; comms_events projects from this collection rather than replacing it.
- CHANGED broadcasts/{auto}. Adds excludedKinfolkIds (the decision C.iii per-recipient removals, so the record is honest about who the operator pulled out), previewedRecipientCount (what the preview promised, sitting next to what actually sent, as a divergence smoke alarm), and previewSnapshotId. Named misses are NOT stored here as an array; they are the durable skipped rows in comms_events tagged with broadcastId, which is queryable, expandable, and lands on the household timeline. Rules unchanged (read isAuntie, write false, firestore.rules:661).
- CHANGED kinfolk/{id}. Adds smsConsent {status:'granted'|'revoked'|'unknown', capturedAtMs, source:'inbound_text'|'portal_signup'|'operator_attested', note}. This exists because A2P 10DLC campaign registration attests to an opt-in flow that carriers can audit, TCPA damages run 500 to 1500 dollars per message, and there is currently no consent record anywhere except portal notificationPrefs.marketingOptIn which only covers users who have a uid. Auto-captured as 'inbound_text' by twilioInbound when a matched household texts first. Missing consent becomes a NAMED MISS with reason no_sms_consent, which slots into decision C.i at zero extra UI cost. Also adds lastCommsAtMs and lastCommsChannel, maintained by the onCommsEventCreate trigger, so the Directory can show 'nothing heard in 9 days' without a per-row subcollection query.
- CHANGED read of kin/{id}, no schema change, new reader. The broadcast resolver gains a kin-collection join grouped by kin.kinfolkId (field confirmed present at auntieos-admin/src/api/directory.ts:128) to build in-memory petTags (union of kin.tags across the household's pets), petSpecies and petNames. Index-free and consistent with the fetch-and-filter-in-memory rationale documented at audienceCriteria.ts:15-18. This is what makes 'all the diabetic dogs' targetable and what supplies the {{petNames}} merge value.
- CHANGED audienceCriteria.ts CriteriaSchema (:24-46): add kind 'petTags' reusing the existing tags and tagMatch fields. KinfolkLike (:52-60) gains petTags, petSpecies and petNames. matchesCriteria (:67) and describeCriteria (:101) extended. Note that tag comparison is verbatim and case-sensitive (:80-84), which is why the composer's free-text tag inputs must become vocabulary-bound pickers.
- NEW call_recordings/{recordingSid}. Splits the durable audio pointer from the mutable call doc. Fields: recordingSid, callSid, kinfolkId, durationSec, recordedAtMs, archive {provider:'cloudinary', publicId, resourceType:'video', deliveryType:'authenticated', format:'mp3'}, archiveState ('pending'|'archived'|'archived_twilio_orphaned'|'failed'|'purged'), archiveError, expiresAtMs. Exists because voicemails.audioUrl today is a bare body.RecordingUrl (twilioInbound.ts:242) requiring HTTP Basic auth with the account credentials, so it can never be an audio src on any platform. The raw Twilio URI is never stored in a client-readable field and never sent to a client.
- MERGE FIELD VOCABULARY, four tokens, no new collection: {{firstName}}, {{lastName}}, {{householdName}}, {{petNames}}. Resolved server-side per recipient for BOTH channels at send. previewBroadcastAudience returns the resolved map for the CURRENTLY SELECTED preview recipient only (switching recipients costs one call), plus emptyMergeFields (field names only, no values) for every matched recipient so decision D's warning can name who a token blanks for without shipping the whole directory's merge data to the client on every keystroke. Capped at four plain substitutions with no helpers or conditionals, because a 10-line pure function can be proven equivalent across TS and Kotlin against one shared fixture table and a Handlebars subset cannot.
- DELETED: marketingBlasts and scheduleMarketingBlast (scheduleMarketingBlast.ts:59/:72). Deployed ACTIVE, zero documents, zero callers on any platform. Removed rather than wired, because keeping it means two competing broadcast concepts in one codebase.
- DELETED as a read target: the `emails` collection. It does not exist in the live database and has no writer in either function codebase, yet android AuntieRepository.kt:2265-2269 and the wasm emailsStream both read it. Both readers are deleted. The Email lane is fed instead by comms_events where lane == 'email', projected from external_messages, which has a real writer.
- RETENTION AND ERASURE, shipped with the writers, not after them. expiresAtMs is stamped at write time and enforced by a Firestore TTL policy on comms_events, sms_messages, calls_log, voicemails and call_recordings. Unmatched inbound (kinfolkId empty) gets 90 days, because wrong numbers, spam and one-off strangers are pure liability with zero decision value; the field is cleared in the same write when such a row is later matched to a household. Matched household comms and recordings get an operator-visible retentionDays on business_settings, defaulting to 400 days. Nothing declares a retention policy that no code enforces: the field and the purge job ship in the same slice or neither does.

## Risks
- PREVIEW AND SEND DIVERGING is the top risk and the reason computeReachability is a refactor rather than an optimization. A summary that disagrees with the send is worse than no summary, because she will trust it. Mitigated structurally (one exported pure function, two call sites, one fixture suite) and detected in production by storing previewedRecipientCount next to recipientCount on the broadcasts doc so a mismatch is visible after the fact.
- MERGE RENDERER DRIFT across three implementations (server at send, TS in React, Kotlin in Compose) would mean the preview lies about what the customer receives. Mitigated by capping the vocabulary at four plain substitutions with no helpers, having the server resolve VALUES and the clients do only string replacement, proving both client renderers against one shared fixture table, and keeping stripUnresolvedTokens as the server-side belt so a divergence blanks a token rather than leaking it.
- A2P CAMPAIGN VETTING IS OUTSIDE OUR CONTROL and Twilio documents it as taking up to several weeks for a first-time registrant. This is why the paperwork is filed in slice 1's week while the code lands in slice 5, and why inbound is split out first: inbound needs no approval, so slices 1 through 4 have real data regardless of the queue. It is tracked as a dated, visible roadmap flag, not as a one-line dependency. One operator answer gates the filing on day one: EIN or no EIN, which picks sole-proprietor brand (cheaper, capped at one campaign, lower throughput) versus standard brand.
- EVERY CALLS AND EMAIL SURFACE READS EMPTY UNTIL SLICE 1'S REPOINT LANDS, and this will read as 'the redesign did not work'. Mitigated by shipping the repoint inside slice 1 rather than after it, and by requiring each empty lane to carry a specific banner naming the cause rather than a generic empty state.
- PROJECTION DRIFT. comms_events is a copy, and a failed trigger means the Inbox silently loses a message, the worst failure this product can have. Mitigated by doc ids derived from source ids so replays upsert, by keeping every source collection as a write-only archive so a full rebuild is always possible, by reconciling rather than appending in rebuildCommsTimeline, and by alerting on trigger failure through the Sentry integration already in place. I explicitly did NOT build a nightly reconcile cron plus a comms_spine_health collection plus a drift banner: that is monitoring infrastructure for a multi-tenant platform with an incident-response process, and this business has one person and idempotent upserts.
- RECORDINGS ARE THE MOST SENSITIVE DATA THIS PRODUCT WILL EVER HOLD, and this design makes them playable from a web browser for the first time. Controls: Cloudinary authenticated delivery, 2-minute signed URLs, the Sentry query-string scrubber shipped before the player, the Twilio-side original deleted after archive, an enforced expiry, no test-admin read, and the Public play-recording.js proxy deleted in slice 1 with its two email callers repointed. Note honestly that COMMS_RECORDING_URL_MINTED is a URL-issuance record, not a playback log, and that with one admin who is also the only reader of ActivityLog, comms auditing is forensic and demonstrative rather than preventive.
- CARD NUMBERS ON A RECORDED LINE. Texas one-party consent settles that recording is lawful; it does not make recording everything safe. A card number spoken into a recorded call becomes stored cardholder data that PCI-DSS prohibits retaining, and recording is configured by a Studio widget that this design leaves untouched, so there is no mid-call pause. The chosen answer is explicit rather than silent: a written operator policy that card numbers are never taken on a recorded line, plus the enforced recording expiry so the window is finite regardless. If the operator says she does take card details by phone, slice 9's native call screen gains a pause control against CallInviteManager state and the Studio edit comes into scope.
- DELETING SOURCE-COLLECTION READERS AND FLIPPING THEIR WRITE RULES must happen only after inbound is verified writing server-side, which is why it sits in slice 4 rather than slice 1. Doing it early replaces empty screens with permission-denied banners. Before repointing, confirm reconcile_comms.py is genuinely dead: it queries reconcileStatus == 'pending' on all three collections and was flagged recommend-delete in the 2026-06-18 review, and a recommendation is not a confirmed deletion. This is a blocking checkpoint at the start of slice 4, not a prose note.
- THE PER-CHANNEL INBOX IS RECORDED AS CONTESTED AND HONOURED AS WRITTEN. Her day is organized by person and time, not by pipe, and in the moment a text arrives while she is driving she does not think 'I will go to the Calls tab'. Decision A is settled and this design implements it without hedging: tabs by channel on every surface. The field moment is answered instead by slice 1's lock-screen inline reply, which is the real fix and does not relitigate the decision. If she later wants an All lane it is a one-line addition over the same index.
- TWO TAG NAMESPACES WITH VERBATIM CASE-SENSITIVE MATCHING. kinfolk.tags and kin.tags share one vocabulary editor but two scopes, and matchesCriteria compares tag strings exactly (audienceCriteria.ts:80-84). Saved segments store names rather than ids, so renaming a tag silently orphans every segment referencing it. Flagged, not solved inside this project. The vocabulary-bound picker in slice 6 at least kills the typo-on-entry case, which today fails only after the operator confirms a send.
- THE CLOUDINARY OPTIMIZATION PATH DEPENDS ON A SECRET THAT IS CURRENTLY WRONG. CLOUDINARY_API_SECRET versions 2 and 3 are byte-identical and both return 401 from Cloudinary /ping; version 1 is the working value and the live signer mounts version 3. Verify and correct the mounted version before slice 8 begins, or archiveCallRecording will fail on every upload.
- TRI-PLATFORM COST FOR COMMS SPECIFICALLY IS ACCEPTED, NOT ASSUMED. Every comms surface here is built three times for one user. Desktop JVM is a project non-negotiable and shares commonMain with wasm, so the marginal cost over wasm is small, but it is real per slice. Naming it rather than quietly paying it: if the operator confirms she does not open desktop for comms, slices 3, 4, 6 and 8 can drop the desktop verification pass while still compiling, and that is her call to make, not mine to take.
- THE EMAIL LANE IS AN OUTBOUND SENT LOG, NOT AN INBOX. There is no inbound email capture anywhere in this system and none is being built. If the operator expects to see replies to her emails there, that expectation needs resetting before slice 4 ships, which is why the lane carries a standing label rather than an empty list that implies mail might one day appear.

## Not building
- WhatsApp, cut from the roadmap entirely rather than scheduled. Two of the three reviewers independently flagged it as building for a user who does not exist: no client has asked, marketing templates to US numbers have been undeliverable since April 2025 (error 63049) so broadcasts stay SMS and email permanently, every business-initiated message needs a Meta-approved contentSid rather than a body, and Meta business verification takes weeks of the operator's attention that the A2P registration needs more. What IS built is the seam: channel and lane are fields, the sender resolver is channel-aware, and twilioInbound strips a whatsapp: prefix, so adding it later is one function and a renderer. GATE to reconsider: three or more households independently ask to message via WhatsApp.
- Twilio Conversations API. Genuinely the unified model and free below 200 active users, and the account is half-provisioned for it, but Twilio has renamed it Conversations (classic) and steers new work to Conversation Orchestrator, it is a real rewrite of the send path plus an extension of the SEND_SUPPRESS stub, and it buys cross-channel threading for a system that currently holds two conversation documents. Revisit when there is actual cross-channel history to thread.
- A nightly reconcileCommsSpine cron, a comms_spine_health collection, and an Inbox drift banner. Monitoring-team infrastructure for a platform with tenants and an incident process. Idempotent upserts plus retained source collections plus Sentry alerting on trigger failure cover the same failure at this volume without a permanent collection, rules and a banner she has to learn to read.
- BulkWriter in the broadcast fan-out. Pre-solving a throughput problem the analysis says does not exist at 34 households on 2 channels inside a 540s timeout. Plain awaited writes; introduce BulkWriter only if an observed run approaches the timeout.
- A comms_raw archive of verified webhook payloads plus a durability field distinguishing projected from authoritative rows. The cheaper answer to the same problem is keeping the source collections, which already ARE that archive and cost nothing at 0 documents, and which make the durability distinction unnecessary because nothing is authoritative-only.
- A comms_threads summary collection. Client-side grouping inside a bounded window is correct at solo-operator volume and avoids a second transactionally maintained denormalization. The visible 'showing the most recent 200' affordance is the trigger to revisit, and it ships in slice 4 rather than waiting for someone to notice.
- A 'showing first 500 of N' truncation UI in the recipient roster. The zod bound stays as a cheap defensive cap, but building the disclosure copy for a ceiling this business will not approach is the same anti-pattern as building UI for empty collections. The roster shows all N.
- A composition breakdown as its own callable response field. Computed client-side from the recipients array the preview already returns, which removes a response-shape surface for the least load-bearing of decision C's three panels.
- Full merge maps for every matched recipient on every keystroke. That is a continuous directory dump crossing the wire and sitting in client memory during composition, on surfaces with Sentry initialized. Only the selected preview recipient's merge map is returned; the switcher refetches; empty-token warnings ride on field names only.
- Cost estimation in the broadcast composer, in any disguise. Explicitly rejected by the operator, and not smuggled back as a segment count or a 'this will use N messages' hint.
- A recording disclosure in the IVR. Texas is one-party consent and the operator is a party to every call.
- A saved audience segment picker in React. saveAudienceSegment, listAudienceSegments and deleteAudienceSegment are deployed ACTIVE and both Kotlin surfaces call them, but audience_segments has zero documents and the operator has not completed a single broadcast. Saving a reusable filter is a feature for someone who repeats a filter. GATE: she builds the same criteria twice.
- A consent capture UI, a compliance dashboard, or a retention settings screen. The kinfolk.smsConsent field, its auto-capture from inbound text, and a single attestation control on the existing profile ship because A2P registration attests to an opt-in flow and the field is unretrofittable. A program around it is scope she did not ask for.
- A separate modelUseAllowed boolean. The authorship field plus kinfolkId plus smsConsent already answer which message text is the operator's to reuse, so a second flag is derivable rather than captured.
- A mid-call recording pause control and any Twilio Studio flow edits. The three existing flows and the IVR stay untouched; this design consumes their callbacks. Reconsider only if the operator confirms she takes card details by phone, in which case slice 9's native call screen is where it lands.
- The inapp and push broadcast channels in any composer. broadcastMessage supports four and android's Broadcast.kt exposes all four, but the inapp path (:179-201) deliberately writes notifications with channels:[] to bypass the catalog fan-out, which makes it a second parallel notification system with no template and no gate. Email and SMS only, matching what React already ships.
- An inbound email channel. There is no inbound parse anywhere in this system. The Email lane is labelled an outbound sent log rather than pretending mail arrives there.
- Full-text search across comms history. Firestore cannot do it natively and it needs a search index this project does not have. Time-ordered plus per-household plus per-channel covers the day.
- Broadcast scheduling, drip sequences, A/B testing, open-rate dashboards, rich text or MMS in the broadcast body, and read receipts beyond the readAt already stamped at lib/conversations.ts:180. She is one person sending a schedule change to a few dozen households.
- A third-party helpdesk (Front, Missive, Intercom). Fixed monthly cost larger than the projected Twilio bill for a one-person business, and it splits the source of truth for customer communication between Firestore and a vendor inbox, which undermines the dossier pipeline and the activity_log discipline this project mandates.
- A second asset store. Cloudinary is already the asset store and already has a signer; a Firebase Storage bucket for audio would be a new surface with new rules and no gain.
- An audit entry per previewBroadcastAudience call. It fires on debounced criteria changes and would bury the real send entries. COMMS_BROADCAST_PREVIEWED is written once per confirmed preview snapshot, carrying criteria and counts, not names. Inbound event arrival and mark-read are not audited either.
- Rebuilding the wasm admin surface's comms screens for their own sake. The wasm admin is throwaway. The Compose work lands in web/composeApp/src/commonMain because desktop JVM is first-class and shares that source set; wasm inherits it and gets no bespoke attention.
