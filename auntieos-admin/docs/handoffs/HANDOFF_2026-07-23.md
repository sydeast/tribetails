# Handoff, 2026-07-23

Follows `HANDOFF_2026-07-22.md`.

Five PRs (#25 to #29) merged and deployed. Two production outages were found and
closed. One of them I caused; the other had been live for two days and nobody
knew, because nothing alerts.

## Start here

**Sign-in was broken and the cause was not what anyone would have guessed.**
`auth/internal-error` on auntie.tribetails.com. The real server response was
`400 MISSING_RECAPTCHA_TOKEN`, and the browser console said why: loading
`https://www.google.com/recaptcha/enterprise.js` "violates the following Content
Security Policy directive: script-src 'self'".

reCAPTCHA Enterprise is configured on this project, so the Auth SDK must fetch
`enterprise.js` and attach a token to `signInWithPassword`. The admin's CSP
shipped `script-src 'self'` and `frame-src 'none'`, so the script could never
load and the challenge iframe could never render.

The header block came from the 2026-07-21 change titled "give the live admin the
security headers the superseded site already had". It did not copy them. The
wasm site's still-present CSP allows `www.gstatic.com`, `www.google.com`,
`apis.google.com` and `www.recaptcha.net` in `script-src` plus the matching
`frame-src`; the admin's copy dropped all of them. So this admin has never been
able to complete a sign-in under that policy. It stayed invisible because a
refresh token does not re-run sign-in, so an authenticated session kept working
until it had to re-authenticate.

**The trap, recorded so the next person does not fall in it.** Identity Toolkit
validates reCAPTCHA BEFORE dispatching a blocking function. So `beforeSignIn`
was never invoked, and its Cloud Run request log showed zero `Google-Firebase`
calls for two days. That reads exactly like a broken blocking-function
registration, and it sent the whole investigation at the function, its
registration, its IAM and its revisions. All were healthy the entire time.
`beforeSignIn` was even redeployed to "re-register the trigger", which did
nothing. **If sign-in fails and the blocking function shows no invocations, that
is a symptom, not the cause. Get the `signInWithPassword` response body first.**

Fixed in #29, deployed, and verified by driving the real form with a deliberately
wrong password: it now returns "Email or password is incorrect" instead of
`auth/internal-error`, with no CSP violations. The Kinfolk portal was never
affected; both its targets already allow the reCAPTCHA origins.

Deploy note carried forward: a `functions:mytribe` deploy hits two Cloud Run
quota walls at 213 functions, first "Per project mutation requests per minute",

deploy single functions by name.

## What the review found

A 7-lane parallel review of the whole monorepo produced 13 P0s. Report:
`docs/reviews/2026-07-23-full-stack-review.md`. Highlights beyond the outage:

- **`businessSettings/admins` had two readers and no writer, and did not exist.**
  16 catalog keys name `businessAdmins` as their PRIMARY resolver, so booking
  requests, inbound messages and bad ratings have NEVER notified the operator,
  and every portal-created visit was written `assignedAuntieUid: null`. Nothing
  in the system could create the document. Fixed with a resolver plus three
  named write intents (add / set / remove) over one guarded core.
- **Two Firestore rules gaps made Android features silently dead.** `fcm_tokens`
  had a rule under the wrong name (`fcmTokens`), and `enhanced_bookings` had no
  rule at all. With no catch-all in the file, both were default-deny.
- **Two Android decode crashes.** `VetClinic` and `UserProfile` typed
  `createdAt`/`updatedAt` as `String` while a server writer stamped
  `serverTimestamp()`, taking down the whole snapshot listener.
- **`/api/send-message` proxied the retired n8n**, so every 1:1 operator send
  failed while Broadcast beside it worked.
- **The test suite hides failures.** `test/_helpers/mockDb.ts` implements
  `.where()`, `.orderBy()` and `.limit()` as NO-OPS across 99 test files, so
  every filter and sort assertion is vacuous. Still open, and it is the largest
  remaining item.

## Gotchas

- **`firebase functions:log` returned data 30+ hours stale tonight**, including
  omitting a request I had just made. Do not conclude "never invoked" or "no
  errors" from it. `gcloud logging read` is authoritative but slow (3 to 6
  minutes) and sometimes hangs; validate any query by confirming it returns a
  row you know exists before trusting an empty result.
- `gcloud run services get-iam-policy` hangs here. The REST API
  (`run.googleapis.com/v2/.../services/{name}:getIamPolicy`) returns instantly.
- The Identity Platform admin API needs `x-goog-user-project`; without it you get
  a 403 whose body will silently parse as an empty config if you are careless.
- `secret-guard.sh` blocks any Bash command containing the literal `.env`. Use
  the Read/Write/Edit tools for those files.
- A `latestReady == latestCreated` check is the real signal for whether a
  function deployed; `updateTime` moves even on a failed push.

## The pattern worth carrying forward

Ten of the thirteen P0s failed silently, and four had a PASSING TEST standing
over the failure. That is why three days of green CI and a full prod deploy
surfaced none of it.

Six findings were the same shape: the correct fix already existed elsewhere in
the tree and one site was missed. `staffGate` bypassed in one handler, `Any?`
timestamps on three models but not two others, `SetOptions.merge()` on four
write paths but not the fifth, `onError` on the invoice detail screen but not
the list, an `onSnapshot` error callback on the messages listener but not
breadcrumbs, `kinfolkId` threaded through fifteen `PortalApi` calls but not
`getMyAccount`. When fixing one, grep for the pattern's other instances.
