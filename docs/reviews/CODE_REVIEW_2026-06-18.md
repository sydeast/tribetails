### CRITICAL-1. OkHttp BODY-level logging ships in release builds, leaking Firebase ID tokens and message PII to logcat
- **Area / persona:** android_frontend / security_auditor  (confidence 0.92)
- **Location:** `android/app/src/main/java/com/tribetails/auntieos/data/api/RetrofitClient.kt:63-65 (used by buildN8n:16-30, buildTwilio:33-46)`
- **Problem:** loggingInterceptor() unconditionally sets HttpLoggingInterceptor.Level.BODY and is attached to the n8n and Twilio OkHttp clients with no BuildConfig.DEBUG gate (the only DEBUG check in the codebase is in SettingsScreen.kt:245). The n8n client carries the `sendMessage` call (AuntieRepository.kt:538 passes `"Bearer $idToken"` plus the SMS/email body to kinfolk) and `generateViaFunction` (AuntieRepository.kt:492, same Bearer header). Level.BODY logs all request headers (including the Authorization: Bearer <Firebase ID token>) and full request/response bodies to Android logcat in every build variant, including release. The Twilio client similarly logs the voice access token response.
- **Impact:** In production APKs, any process able to read logcat (other apps on rooted devices, ADB during support sessions, crash/log-capture tooling) can harvest valid Firebase ID tokens (impersonate the admin against all callables/Firestore for the token's ~1h lifetime) and the plaintext content of every outbound message to clients. Direct PII + credential exposure.
- **Fix:** Gate the interceptor: `level = if (BuildConfig.DEBUG) Level.BODY else Level.NONE`, or redact the Authorization header and bodies. Do not attach BODY logging to any client that carries auth tokens or message content in release builds.
- **Verified at:** `android/app/src/main/java/com/tribetails/auntieos/data/api/RetrofitClient.kt:63`, `android/app/src/main/java/com/tribetails/auntieos/data/api/RetrofitClient.kt:21`, `android/app/src/main/java/com/tribetails/auntieos/data/api/RetrofitClient.kt:37`, `android/app/src/main/java/com/tribetails/auntieos/data/api/N8nApi.kt:18`, `android/app/src/main/java/com/tribetails/auntieos/data/api/N8nApi.kt:27`, `android/app/src/main/java/com/tribetails/auntieos/data/repository/AuntieRepository.kt:492`

### CRITICAL-2. Test-admin sandbox: update of any LIVE doc by re-tagging kinfolkId (testOwnsIncoming on update breaks isolation)
- **Area / persona:** firestore_rules / security_auditor  (confidence 0.83)
- **Location:** `MyTribe/firestore.rules:152,160,168,189,558,563 (mirror: AuntieOS/web/firestore.rules same lines)`
- **Problem:** On the scoped flat collections (kin, invoices, kin_care_reports, kin_care_sessions, media_files, payments) the rule is `allow create, update: if isAuntie() || testOwnsIncoming()`. testOwnsIncoming() (line 105) checks only `request.resource.data.kinfolkId == testScope()` - the INCOMING/merged payload - not the existing doc. For an UPDATE, request.resource.data is the existing doc merged with the write, so a test admin can target any LIVE document id and do `.update({kinfolkId: <their testScope()>})`: the merged kinfolkId equals testScope() and the write is ALLOWED. The design doc (AuntieOS/docs/2026-06-05-stage-0I-test-admin-sandbox.md line 28-30) explicitly specifies update should gate on `resource.data.kinfolkId` (existing) and only CREATE on `request.resource.data.kinfolkId`; the implementation collapsed both into the incoming check. The rules test (functions/test/rules/testAdminSandbox.test.ts line 111-116) only tries updating a live doc with the WRONG scope (LIVE_TRIBE), which correctly fails - it never tests supplying the CORRECT testScope() against a live doc id, so the hole is uncovered.
- **Impact:** A non-admin sandbox account (no admin:true claim) can write to / re-tag production invoices, payments, kin, sessions, KinTales and media of real clients, pulling them into its sandbox (which it can then read) and corrupting live financial/care data. This defeats the entire 'hard, rules-enforced' isolation guarantee of Stage 0I. Requires knowing or guessing a live document id; ids for these collections are often deterministic (e.g. visit/session id schemes), raising feasibility.
- **Fix:** Use the existing-doc check on update: split the rule into `allow create: if isAuntie() || testOwnsIncoming();` and `allow update: if isAuntie() || testOwnsExisting();` for all six collections. Add a rules-unit test that seeds a LIVE doc and asserts a test admin update with `{kinfolkId: TEST_TRIBE}` FAILS.
- **Verified at:** `MyTribe/firestore.rules:99-107 (testOwnsExisting uses resource.data; testOwnsIncoming uses request.resource.data)`, `MyTribe/firestore.rules:152 (kin: allow create, update: if isAuntie() || testOwnsIncoming())`, `MyTribe/firestore.rules:160 (invoices same)`, `MyTribe/firestore.rules:168 (kin_care_reports same)`, `MyTribe/firestore.rules:189 (kin_care_sessions same)`, `MyTribe/firestore.rules:558 (media_files same)`

### CRITICAL-3. redeemCredit double-redeem race: non-transactional idempotency check enables double Stripe refund / double account-balance credit
- **Area / persona:** mytribe_callables / saboteur  (confidence 0.92)
- **Location:** `functions/src/portal/redeemCredit.ts:43-94`
- **Problem:** redeemCreditHandler reads the invoice, checks `if (inv['creditRedeemedAt'] != null) throw ... 'Credit already redeemed.'` (line 57), then performs the side effect (Stripe `refunds.create` at line 75, or `accountBalanceCents` FieldValue.increment at line 79), and only AFTER that writes `creditRedeemedAt` (lines 84-94). The read, the guard, and the write are NOT in a Firestore transaction. Two concurrent invocations (double-tap, retry, two devices) both read creditRedeemedAt==null, both pass the guard, and both execute the refund/increment. Stripe `refunds.create` has no idempotency key, so the customer is refunded twice; the accountBalance path increments twice.
- **Impact:** Direct monetary loss: a credit can be cashed out two or more times - double real-money Stripe refund, or doubled store credit on families/{kinfolkId}.accountBalanceCents. Triggerable by any kinfolk with a credit invoice simply by firing the call twice in parallel.
- **Fix:** Move the whole flow into db().runTransaction: tx.get the invoice, re-check creditRedeemedAt inside the tx, and tx.set the creditRedeemedAt/creditTarget stamp inside the same tx so a concurrent second call fails the precondition. For the Stripe leg, pass an idempotencyKey (e.g. `credit-${invoiceId}`) to refunds.create so even a retry after a crash cannot double-refund; reserve/stamp the invoice before calling Stripe, or use a dedicated ledger doc keyed by invoiceId.
- **Verified at:** `functions/src/portal/redeemCredit.ts:44`, `functions/src/portal/redeemCredit.ts:57`, `functions/src/portal/redeemCredit.ts:75`, `functions/src/portal/redeemCredit.ts:79`, `functions/src/portal/redeemCredit.ts:84`, `functions/src/lib/wrapCallable.ts:10`

### CRITICAL-5. Source log marked applied AFTER dossier/411 writes - no claim-first or transaction, so a crash/retry double-merges facts
- **Area / persona:** python_reconcile / saboteur  (confidence 0.85)
- **Location:** `web/functions-python/reconcile_comms.py:557-566 (and root twin reconcile_comms.py:472-481)`
- **Problem:** reconcile_pass does: claude_merge -> upsert_dossier (set merge=True, appends to rawSummary) -> upsert_kin411 -> ONLY THEN db.collection(coll).document(log_id).update({reconcileStatus:'applied'}). There is no transaction and no claim-first flip to an in-progress state. If the worker dies, times out (nightly_reconcile timeout_sec=540 with max_per_run=500 doing 500+ sequential Claude calls), or the final update() throws after the dossier write succeeds, the source doc stays reconcileStatus='pending'. The next pass re-runs claude_merge on the same log against the now-already-updated rawSummary and appends the same facts again. Scheduler retries and the --watch loop make overlapping/re-runs realistic. upsert_dossier/upsert_kin411 are not idempotent on log_id: the only guard is lastReconcileSourceLogIds (capped at 10 and never consulted before merging).
- **Impact:** Dossiers and 411s accumulate duplicated bullet lines / re-extracted fields on every retry or timeout, corrupting the rolling summary that the generator reads. Silent data corruption, not a crash.
- **Fix:** Claim the doc first: in a Firestore transaction, read reconcileStatus, abort if not 'pending', set it to 'in_progress' (with a lease timestamp), then do the merge, then set 'applied'. Or de-dup inside upsert_*: if source_id already in lastReconcileSourceLogIds, skip the merge. At minimum mark 'applied' before/transactionally-with the dossier write.
- **Verified at:** `web/functions-python/reconcile_comms.py:560`, `web/functions-python/reconcile_comms.py:562-566`, `web/functions-python/reconcile_comms.py:424`, `web/functions-python/reconcile_comms.py:438-441`, `web/functions-python/reconcile_comms.py:471`, `web/functions-python/reconcile_comms.py:479`

### WARNING-10. getActivityLog() reads the entire append-only audit collection with no limit/order/pagination
- **Area / persona:** android_frontend / new_hire  (confidence 0.78)
- **Location:** `android/app/src/main/java/com/tribetails/auntieos/data/repository/AuntieRepository.kt:2076-2080 (consumed by AdminDataViewModel.kt:325)`
- **Problem:** getActivityLog() does `firestore.collection("activity_log").get()` and toObjects the whole thing. activity_log is the SHA-256-chained audit trail that grows on every admin action and is never pruned. There is no .limit(), no .orderBy(), and no pagination. Other broad reads (getCalls/getVoicemails/getSmsMessages) at least cap via observe* limits, but the one-shot audit-log read is unbounded.
- **Impact:** As the audit log accumulates (it is intentionally append-only and immutable), this download grows without bound - increasing Firestore read cost, latency, and eventually risking OOM/ANR on the ActivityLog screen on older devices.
